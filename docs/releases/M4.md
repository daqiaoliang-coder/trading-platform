# M4 发布说明：在线分片迁移与弹性扩容

- 发布日期：2026-11-03
- 版本：v0.1.0（M4）
- 范围：`trading-replication`、`trading-node`、`trading-loadgen`、`control-plane`

## 概览

M4 将分片复制组从固定成员集升级为可在运行期迁移的成员集。新增 Rust 节点管理 API 与 Go 控制面，支持扩容、缩容、主副本搬迁和定点替换四种迁移模式。迁移只冻结目标分片，其他分片持续服务；旧主在该分片的冻结窗口内退役，新主当选后原子发布新的路由 epoch。

本次发布完成了 M4 的全部验收项：迁移期间无双重主、无已提交交易丢失或重复执行；只有被迁移分片出现受控短暂停写；路由版本收敛且旧主被可靠 fence；并在持续压测下记录了 P99/P999 与停写窗口。

## 主要变化

### 在线迁移编排（`trading-replication`）

- `ReplicatedShard` 支持运行期创建、停止、退役和丢弃副本，副本集合不再固定。
- 目标副本以 learner 加入，经快照与 WAL 追赶；先用 `catchup_lag`（默认 8）判断基本追平，再在冻结窗口内执行精确位点校验（lag=0）。
- 成员变更使用 `ReplaceAllVoters`；变更提交后同步目标副本的成员日志，再退役旧主，避免目标因日志落后而在选举中反复失败。
- 分片级提交闸门 `RwLock<()>`：普通提交取读锁，迁移冻结取写锁。冻结会先排空在途提交，因此停写是有界等待，不是请求失败。
- 旧主在当前分片闸门内停止，并写入 `retired-{id}` 标记；重启后不会被副本发现逻辑选中，不能成为 voter 或 leader。
- 目标主选举会先抑制其他存活副本发起选举，并在旧主任期租约到期后重试；选举预算耗尽时回退到任意存活 voter，避免长时间停写。
- 路由表逻辑槽位映射在迁移中保持不变；物理 voter 集变化后提升 epoch，并原子写入 `data_dir/route.version`（临时文件 + rename + 父目录 fsync）。
- 客户端使用缓存路由提交时，epoch 不匹配返回 `StaleRoute { current }`；刷新路由后用同一 `request_id` 重试，状态机幂等去重。

迁移序列：

```text
create target replica
  -> add learner
  -> catch up (lag <= 8)
  -> freeze shard submits
  -> exact position check (lag = 0)
  -> membership change (ReplaceAllVoters)
  -> sync membership entries to target
  -> retire and fence old primary
  -> elect target leader (lease-aware)
  -> publish route epoch atomically
```

### 迁移结果与失败恢复

- `Completed`：voter 集变更、旧主退役、新主当选和 epoch 发布全部成功。
- `RolledBack`：失败发生在成员变更提交之前。丢弃目标副本，旧 voter 集与 epoch 保持不变，分片继续服务。
- `Degraded`：成员变更已提交，但后续步骤（退役、选举或 epoch 发布）失败。不执行不安全回滚，保留已提交的 voter 集并发布 epoch，等待人工处理。

### 节点管理进程（`trading-node`）

新增二进制 `trading-node`，托管复制集群并暴露本地运维管理 API：

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| GET | `/admin/health` | 节点状态、路由版本、分片数 |
| GET | `/admin/routes` | 当前路由版本与槽位 |
| GET | `/admin/shards` | 所有分片的 voter/learner/leader 布局 |
| GET | `/admin/shards/{id}` | 单分片布局与副本位点 |
| POST | `/admin/shards/{id}/migrate` | 执行一次迁移并同步返回完整报告 |
| POST | `/admin/shutdown` | 优雅关闭 |

迁移接口返回 `200 completed`、`409 rolled-back`、`503 degraded`。支持故障注入 `"fault":"crash-target-before-learner"` 用于回滚演练。

### Go 控制面（`control-plane`）

新增基于标准库 HTTP 的单实例控制面：

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| GET | `/healthz` | 控制面与节点健康状态 |
| GET | `/v1/node` | 节点健康、分片与路由快照 |
| GET | `/v1/shards` | 分片物理布局 |
| GET | `/v1/routes` | 路由版本与槽位 |
| POST | `/v1/shards/{shard}/migrations` | 提交迁移计划 |
| GET | `/v1/migrations` | 迁移历史（新到旧） |
| GET | `/v1/migrations/{id}` | 单次迁移详情 |

控制面在调用节点前完成策略校验：模式参数、目标副本不能已存活、被下线副本必须是 voter、不能少于两个 voter、同一分片不能存在在途迁移。请求携带 `Idempotency-Key` 时，重放返回原记录（`200` + `replayed:true`）。每次尝试先落审计记录再执行，并追加写入 `audit.jsonl`（开始与结束各一次 fsync）。

状态映射：`201 completed`、`409 rolled-back`、`503 degraded`、节点校验失败透传 `400/404/409`、传输失败 `502`。

### 压测与演练（`trading-loadgen`）

新增 `--migrate`：压测进度达到 10% 时在线搬迁分片 0（先扩到第 4 个 voter，再把旧主作为缩容目标退役），输出：

- 迁移状态、epoch/voter/leader 前后值、审计事件时间线；
- `migration_timings`（追赶、冻结、成员切换、选举、总耗时）；
- `migration_pause` 与被迁移分片在窗口内的 P99/max；
- `migration_window` 逐分片 P99/P999/max；
- 路由 epoch 收敛断言与 stale-route 重定向计数。

## 使用方式

启动节点：

```bash
cargo run --release -p trading-node -- \
  --data-dir data/node --shards 4 --replicas 3 \
  --unsafe-buffered --admin-addr 127.0.0.1:8081
```

启动控制面并提交迁移：

```bash
cd control-plane
go run ./cmd/controlplane \
  --addr 127.0.0.1:8080 \
  --node-url http://127.0.0.1:8081 \
  --state-dir control-plane-state

curl -s -X POST http://127.0.0.1:8080/v1/shards/0/migrations \
  -H 'Content-Type: application/json' \
  -H 'Idempotency-Key: shard-0-to-node-4' \
  -d '{"mode":"relocate-leader","target_node":4}'
```

迁移模式：

| 模式 | 语义 | 必填字段 |
| --- | --- | --- |
| `scale-out` | 新增一个 voter，保留现有 voter | `target_node` |
| `relocate-leader` | 用新 voter 替换当前 leader | `target_node` |
| `scale-in` | 移除一个 voter，不新增 | `decommission_node` |
| `replace` | 用新 voter 替换指定 voter | `target_node` + `decommission_node` |

持续压测下执行迁移演练：

```bash
cargo run --release -p trading-loadgen -- \
  --replicas 3 --shards 4 --ops 100000 --concurrency 16 \
  --accounts 256 --unsafe-buffered --migrate
```

### 本机性能基线（release）

环境：macOS Intel x86_64，3 副本、4 分片、16 并发、256 账户、100,000 笔转账、UnsafeBuffered。

| 指标 | 结果 |
| --- | --- |
| 吞吐与正确性 | 15,982 ops/s；100,000 笔全部成功，0 错误 |
| 全量延迟 | P50 286.1us / P99 20.3ms / P999 67.3ms |
| 迁移总耗时 | 1,579ms（追赶 335ms、冻结 40ms、成员切换 25ms、选举 1,090ms） |
| 被迁移分片 | 冻结临界区 40ms；选举阶段约 1.09s；观察 max 1.19s，由客户端重试吸收 |
| 其他分片 | 迁移窗口 P99 18.5–20.3ms、max 19.8–20.3ms，无停写 |
| 路由收敛 | epoch 1 → 2，64 次 stale-route 重定向，0 错误 |
| 数据一致性 | 每个分片每个副本余额 640,000,000,000、账户 64、applied 位点一致 |

说明：`freeze_ms` 只统计成员切换与旧主退役的临界区。停写的主要部分来自旧主退役后的 leader lease 等待：必须等约一个 election timeout，存活 voter 才会接受新主投票。这是当前设计的有意安全边界。

## 兼容性与升级

- 已有 M3 数据目录可直接打开：启动时按现有 `replica-{id}` 目录恢复当前成员集，并跳过 `retired-{id}`。
- `route.version` 不存在时，以配置中的路由版本初始化；之后每次迁移单调递增，重启后不会回退。
- `ReplicatedShardConfig` 新增选主、心跳、快照、并发与超时字段，均有默认值；使用结构体字面量构造时需补 `..Default::default()`。
- 控制面审计为追加式 JSONL，重启时把未完成的 `in-flight` 记录标为 `unknown`，不自动重放。

## 已知边界

- 传输层仍为进程内通道；跨机器副本网络化、真实网络分区与 TLS 属于后续工作。
- `trading-node` 的管理端口不是客户端交易网关，本版本仍未提供网络交易接入。
- 迁移按集群串行化；并行多分片迁移、全局迁移队列与限流尚未实现。
- 逻辑账户→分片槽位映射在迁移中保持不变；改变槽位映射的热点搬迁尚未实现。
- 退役副本保留数据目录，供 fence 演练人工重启，不自动清理。
- Go 控制面为单实例内存索引加 JSONL 审计，无分布式协调、TLS 或鉴权。
